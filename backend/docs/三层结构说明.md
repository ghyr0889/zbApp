# 审批、工作日志、积分看板的三层结构

这三个模块保持原来的接口地址、参数、返回结构和业务规则，前端调用不需要修改，数据库不需要迁移。

| 功能 | 接口层 | 业务层 | 数据访问层 |
| --- | --- | --- | --- |
| 审批查阅 | `routers/review.py` | `services/review_service.py` | `repositories/review_repository.py` |
| 工作查询与管理 | `routers/work_logs.py` | `services/work_logs_service.py` | `repositories/work_logs_repository.py` |
| 积分看板 | `routers/score_board.py` | `services/score_board_service.py` | `repositories/score_board_repository.py` |

## 每层负责什么

- router：保留路由装饰器、请求模型、Query/Depends 参数声明，取得数据库会话，然后调用同名 service 函数。
- service：保留权限校验、业务参数检查、审批状态变化、积分计算和返回结果组装。业务操作中的 commit、rollback、flush 和关系缓存刷新仍在这一层，以保留原来的事务边界。
- repository：负责数据库查询、过滤、排序、分页、预加载关联、SQL 聚合，以及登记新增/删除。不处理 HTTP 请求、不决定调用人的业务权限，也不提交事务。

repository 可以返回 ORM 对象。service 修改对象属性后，SQLAlchemy 会在 flush/commit 时写入修改，不需要为每个属性单独添加保存函数。所有层使用同一次请求传入的数据库会话。

## 以审核拆分申请为例

1. 前端请求 `POST /api/v1/review/split-requests/{request_id}/review`。
2. `routers/review.py` 校验请求格式并调用 `review_service.review_split_request()`。
3. service 调用 repository 查询申请、审核人、工作包和工作项。
4. service 检查角色、申请状态、动作和必填字段，执行批准/驳回/提交逻辑。
5. 新对象通过 repository 登记，service 统一提交；原来会回滚的失败路径仍执行回滚。
6. router 返回 service 的结果。

## 跨模块调用

工作查询和后台管理需要使用积分计算时，直接从 `services.score_board_service` 导入 `compute_calc_score`、`compute_deducted` 或 `monthly_quality_score`，不再从积分 router 导入业务函数。`main.py` 仍然注册原来的三个 router。

现有 `utils.py` 中共享的进度、日期、关闭状态和自动完成申请等辅助功能继续复用。本次没有修改它们的业务规则，也没有把其他 router 一并重构。

## 以后如何修改

- 修改地址、请求参数或依赖注入：修改 router。
- 修改审批规则、积分公式、权限或返回字段：修改 service。
- 修改数据库过滤、排序、预加载或分页查询：修改 repository。
- 新增写业务：由 service 安排步骤和事务，repository 不应在中间提前 commit。

## 验证

在 backend 目录执行：

```text
python -m unittest discover -s tests -v
```

新增 `tests/test_layered_modules.py` 覆盖审批流转与失败回滚、项目/工作包分页、完成申请去重与撤回、删除限制、月度分值及质量分、周期汇总和层间调用边界。测试只使用内存 SQLite。

重构时还比较了原版与新版的 OpenAPI 定义，以及相同测试数据下43次业务调用的返回结果，均保持一致。此验证不代替部署环境下的 MySQL 和浏览器联调。
